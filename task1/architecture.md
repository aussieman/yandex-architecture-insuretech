# Технологическая архитектура InsureTech (to-be)

## Введение

Предложенная архитектура "to-be" для приложения InsureTech разработана для решения проблем быстрого роста, включая медленную загрузку страниц, нарушение SLA для B2B-клиентов, падения приложения и подготовку к рекламной кампании. Архитектура обеспечивает высокую доступность (99,9%), RTO 45 минут, RPO 15 минут, равное время загрузки для пользователей из разных регионов и поддержку 24/7 работы.

## Общая архитектура

Архитектура построена на принципах отказоустойчивости и масштабируемости с использованием нескольких зон доступности (Availability Zones). Основные компоненты распределены между тремя зонами для обеспечения высокой доступности и балансировки нагрузки.

### Ключевые принципы
- **Масштабирование**: Горизонтальное масштабирование с использованием Kubernetes и HPA (Horizontal Pod Autoscaler).
- **Отказоустойчивость**: Active-Passive failover между кластерами Kubernetes в разных зонах.
- **Балансировка нагрузки**: Многоуровневая балансировка с NGINX (с rate limiting), HA Proxy и Kubernetes LoadBalancer.
- **База данных**: Кластеризация PostgreSQL с Patroni и ETCD, потоковая репликация между зонами.
- **Мониторинг**: Prometheus для каждого кластера.

## Компоненты архитектуры

### 1. Зоны доступности (Availability Zones)
Архитектура использует три зоны доступности (Зона 1, Зона 2 и Зона 3), каждая из которых содержит полную копию инфраструктуры. Три зоны обеспечивают лучший кворум для решений о failover (например, в распределенных системах типа ETCD), предотвращают сценарии split-brain, улучшают распределение нагрузки и повышают общую отказоустойчивость по сравнению с двумя зонами.

#### Компоненты в каждой зоне:
- **Load Balancer (NGINX с rate limiting)**: Обрабатывает входящий трафик, ограничивает нагрузку от партнеров (например, до 20 RPS на партнера), распределяет запросы между кластерами Kubernetes.
- **Kubernetes кластеры**:
  - **Кластер 1 (Active)**: Основной кластер, обрабатывающий основную нагрузку.
  - **Кластер 2 (Passive)**: Резервный кластер для failover.
  - Каждый кластер имеет HPA для автоматического масштабирования подов.
  - **InsureTech namespace**: Содержит поды для сервисов:
    - core-app (монолитное приложение)
    - client-info (управление данными клиентов)
    - ins-product-aggregator (агрегация продуктов от страховых компаний)
    - ins-comp-settlement (расчеты со страховыми компаниями)
  - **Prometheus**: Мониторинг и алертинг для кластера.
- **HA Proxy**: Обеспечивает высокую доступность и failover для подключений к базе данных.

### 2. База данных
- **PostgreSQL кластер**: Развернут на отдельных VM (node1 и node2) в каждой зоне.
- **Patroni**: Управляет автоматическим failover и репликацией.
- **ETCD**: Распределенное хранилище для координации кластера.
- **Потоковая репликация**: Синхронизирует данные между зонами для обеспечения RPO 15 минут.
- **pgBackupRest**: Сервер бэкапов для регулярного резервного копирования, обеспечивающего RTO 45 минут.

### 3. Внешние интеграции
- **Пользователи**: Доступ через веб-интерфейс с балансировкой нагрузки.
- **Партнеры (B2B)**: API-доступ через LoadBalancer с rate limiting для предотвращения перегрузки.
- **Страховые компании**: Интеграция через ins-product-aggregator и ins-comp-settlement.

## Масштабирование и отказоустойчивость

### Стратегия масштабирования
- **Горизонтальное масштабирование**: Предпочтительно для Kubernetes подов с HPA на основе CPU/памяти.
- **Дополнительные зоны**: Используются три зоны для географического распределения и снижения latency для пользователей в разных регионах РФ.

### Балансировка нагрузки
- **Уровень 1 (Global)**: DNS-based routing или Global Load Balancer для распределения трафика между зонами.
- **Уровень 2 (Zone)**: NGINX с rate limiting для контроля нагрузки от партнеров.
- **Уровень 3 (Cluster)**: Kubernetes LoadBalancer для распределения внутри кластера.
- **Health checks**: Реализованы на всех уровнях для автоматического переключения на здоровые инстансы.

### Фейловер стратегия
- **Active-Passive**: Один кластер активен, второй пассивен. Переключение происходит автоматически при сбое (health checks).
- **На уровне клиента**: Если зона недоступна, трафик перенаправляется в другие зоны (с использованием кворума из трех зон для надежности).
- **RTO/RPO**: Обеспечивается через репликацию БД и автоматизированный failover.

## База данных

### Конфигурация
- **Кластеризация**: Patroni + ETCD для управления мастером и репликами.
- **Репликация**: Потоковая репликация между зонами для синхронизации данных.
- **Бэкапы**: pgBackupRest для регулярных бэкапов с хранением в облаке.
- **Шардирование**: Не применяется, так как объем данных (50 GB) не требует шардирования на текущем этапе.

## Преимущества архитектуры

- **Высокая доступность**: 99,9% uptime благодаря multi-zone развертыванию с тремя зонами.
- **Масштабируемость**: Автоматическое масштабирование под нагрузкой.
- **Защита от DDoS/перегрузки**: Rate limiting на NGINX.
- **Географическая оптимизация**: Равное время загрузки для пользователей из разных регионов.
- **Отказоустойчивость**: Быстрое восстановление после сбоев.

## Рекомендации по внедрению

1. Начать с развертывания в одной зоне, затем добавить вторую и третью.
2. Настроить мониторинг и алертинг в Prometheus.
3. Протестировать failover сценарии.
4. Оптимизировать rate limits на основе реальной нагрузки партнеров.
5. Регулярно тестировать бэкапы и репликацию.

Эта архитектура решает все заявленные проблемы и обеспечивает устойчивый рост InsureTech.
