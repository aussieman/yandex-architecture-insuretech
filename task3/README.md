# Переход на Event-Driven архитектуру

## Текущая архитектура

Система InsureTech состоит из следующих ключевых компонентов:

- **core-app**: Монолитное приложение для отображения доступных страховых продуктов, оформления новых страховок и отображения информации о купленных страховках.
- **ins-product-aggregator**: Сервис для интеграции со страховыми компаниями, предоставляющий единый API для получения информации по страховым продуктам.
- **ins-comp-settlement**: Сервис для осуществления взаиморасчётов со страховыми компаниями.
- **client-info**: Сервис для учёта клиентских данных.

Текущие взаимодействия:
- core-app получает данные о продуктах через REST API от ins-product-aggregator каждые 15 минут.
- ins-comp-settlement получает данные о продуктах через REST API от ins-product-aggregator раз в сутки.
- ins-comp-settlement получает данные об оформленных страховках через REST API от core-app раз в сутки.
- ins-product-aggregator синхронно запрашивает информацию из всех страховых компаний (сейчас 5) и агрегирует её в единый список.

## Проблемы и риски с ростом нагрузки

### Проблемы текущей архитектуры

1. **Синхронные запросы к множеству внешних API**:
   - ins-product-aggregator делает последовательные синхронные запросы ко всем страховым компаниям.
   - При добавлении 5 новых компаний время ответа увеличится пропорционально.
   - Задержки или ошибки в одном API блокируют весь процесс агрегации.

2. **Частые опросы для поддержания актуальности данных**:
   - core-app опрашивает каждые 15 минут, что создаёт постоянную нагрузку.
   - ins-comp-settlement опрашивает раз в сутки, но в ночное время, что может вызвать пиковые нагрузки.

3. **Зависимость от внешних систем**:
   - Ошибки или недоступность API страховых компаний приводят к сбоям в работе сервисов.
   - Нет локального кэширования или резервных механизмов.

4. **Синхронные взаимодействия между сервисами**:
   - ins-comp-settlement зависит от core-app для получения данных о страховках.
   - Любые задержки в core-app влияют на процесс взаиморасчётов.

5. **Отсутствие масштабируемости**:
   - Рост числа компаний требует линейного увеличения ресурсов для обработки запросов.
   - Нет возможности параллельной обработки запросов к разным компаниям.

### Риски с планируемым ростом

1. **Увеличение времени отклика**:
   - С 5 до 10 компаний время агрегации может увеличиться в 2 раза.
   - core-app может не успевать обновлять данные каждые 15 минут.

2. **Повышение вероятности сбоев**:
   - С увеличением числа внешних зависимостей растёт вероятность частичных сбоев.
   - Один недоступный API может сделать всю систему неработоспособной.

3. **Перегрузка внешних систем**:
   - Частые запросы могут быть восприняты страховыми компаниями как DDoS-атака.
   - Могут быть введены ограничения на количество запросов.

4. **Финансовые потери**:
   - Задержки в оформлении страховок могут привести к потере клиентов.
   - Ошибки в расчётах могут вызвать юридические проблемы.

5. **Технический долг**:
   - Текущая архитектура не готова к масштабированию.
   - Необходима полная переработка взаимодействия с внешними системами.

## Предлагаемые решения

Для решения выявленных проблем предлагается перейти на Event-Driven архитектуру, введя новую компоненту - Event Streaming Platform на базе Apache Kafka. Это позволит устранить синхронные зависимости и обеспечить масштабируемость.

### Переход на Event-Driven архитектуру

1. **Введение Event Streaming Platform (Kafka)**:
   - Новая центральная шина событий для асинхронного взаимодействия между сервисами.
   - Топики: product-updates, policy-created, settlement-status.
   - ins-product-aggregator публикует обновления продуктов в топик product-updates.
   - core-app и ins-comp-settlement подписываются на этот топик для автоматического обновления локальных реплик.

2. **Асинхронное взаимодействие между сервисами**:
   - core-app публикует события policy-created при оформлении страховок.
   - ins-comp-settlement подписывается на эти события вместо опроса по REST.

3. **Использование Transactional Outbox паттерна**:
   - Обеспечивает атомарность операций: бизнес-логика и подготовка событий выполняются согласованно.
   - Предотвращает двойную запись и гарантирует надёжную доставку событий.
   - ins-product-aggregator использует таблицу IncomingInfo для временного хранения сообщений до публикации.
   - ins-comp-settlement использует таблицу Outbox для обработки заявок и публикации settlement-status.

### Преимущества решений

- **Устранение синхронных зависимостей**: Сервисы работают независимо.
- **Масштабируемость**: Новые компании могут быть добавлены без изменения логики.
- **Надёжность**: События доставляются гарантированно через Kafka.
- **Производительность**: Нет постоянных опросов, данные обновляются по событиям.

### Обоснование использования Transactional Outbox

Transactional Outbox паттерн решает проблему двойной записи (dual-write problem), когда нужно атомарно сохранить бизнес-данные и опубликовать событие. Без него возможны сценарии, где данные сохранены, но событие не опубликовано, или наоборот, что приводит к несогласованности.

В InsureTech это критично:
- Для ins-product-aggregator: при получении обновлений от страховых компаний данные должны быть сохранены, и событие product-updates опубликовано атомарно.
- Для ins-comp-settlement: при обработке заявок на взаиморасчёты бизнес-операция и событие settlement-status должны быть согласованы.

Паттерн обеспечивает надёжность в распределённой системе, предотвращая потерю данных и обеспечивая eventually consistent state.

### Реализация Transactional Outbox

1. **Для ins-product-aggregator**:
   - Специальная таблица `IncomingInfo` в MemcachedDB (или аналогичном хранилище).
   - При обработке новой информации от страховых компаний: сообщение кладётся в IncomingInfo до полной обработки.
   - Только после успешной публикации в Kafka сообщение удаляется из IncomingInfo.
   - Отмена двойной записи обеспечивается хэшом сообщения с TTL сроком в N дней (например, 20 дней) для предотвращения повторной обработки.

2. **Для ins-comp-settlement**:
   - Таблица `outbox` в ins-comp-settlement-db.
   - При оформлении заявок: сохранение бизнес-данных и вставка события settlement-status в outbox в одной транзакции.
   - Outbox Processor публикует события в Kafka и обновляет статус в outbox (помечает обработанные заявки специальным bool флагом, идентификатором служит ID заявки).
